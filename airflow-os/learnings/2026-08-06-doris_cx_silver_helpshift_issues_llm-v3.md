> 이 파일은 공개 레포에 올라간다. 스키마·실측 수치는 운영 레포 `designs/`의 설계도에 있다.

## 무엇을

helpshift LLM DAG를 두 번 재작성했다. v2: 손수 호출(v1)을 `@task.llm` 3단계로 전환 —
설계→구현→테스트→리뷰까지 통과. **⑤ 승인 직전에 사용자가 코드를 정독하고 가치를 재판단**,
LLM 3단계를 한 호출(output_type 구조화 출력)로 합친 v3로 다시 한 사이클. 최종 4태스크,
v2 대비 순삭제 \~100줄, 테스트 77개, 커밋 완료.

## 왜 (결정과 트레이드오프)

- **v2를 버린 근거는 측정이었다.** v2는 "provider가 재시도를 가져가 코드가 준다"는 약속이었는데
  재보니 오히려 늘었다(+53줄). 지운 것(\~110줄, API 방어)보다 생긴 것(\~160줄, 프레임워크 임피던스 —
  merge·자리보존 장부·Jinja 무해화·검증 비대)이 많았고, 이번 사이클 런타임 지뢰 2건이 **둘 다 새로
  생긴 층에서** 나왔다. 결정적 당근(durable 캐시)도 허상으로 판명.
- **단일 호출이 문제를 구조로 지웠다.** 언어 오표기 사고 방어(휴리스틱 게이트)가 "모델이 원문을
  직접 읽는다"로 불필요해졌고, 단계 사이 합류·자리보존·few-shot 기계장치가 통째로 사라졌다.
  행당 호출도 2\~3회 → 1회로 오히려 싸다.
- **레거시 승계를 중단했다.** few-shot·따옴표 정규화는 "레거시가 그렇게 만들었다"가 유일한 근거
  였다 — 사용자가 "레거시가 좋은 코드가 아니었다"며 끊었고, 품질은 남아 있는 eval 도구로 배포 전
  측정한다(주장 대신 채점).
- **검증은 무음 구멍만.** 팀 내부용 Variable에 빡빡한 필수 키 검증 대신: 기본값 폴백 + "에러가 안
  나는 실패"(프롬프트에 enum 라벨 누락)만 검증. 시끄럽게 터지는 결함은 그냥 터지게 둔다.

## 발견 / 배운 점

1. **"리팩터는 동작 보존" 원칙이 항상 옳지 않다.** 보존할 가치가 측정된 적 없는 동작(레거시
   few-shot)이면, 보존 비용이 재설계 비용보다 클 수 있다. 판단 기준은 "그 동작을 검증한 eval이
   있는가 / 다시 돌릴 수 있는가".
2. **파싱 통과가 mapped task의 kwarg를 검증하지 않는다.** 검증이 unmap(런타임)으로 지연돼,
   없는 파라미터(durable)가 운영 첫 실행에서야 전 행 TypeError로 터진다. 실물 실행 경로 테스트가
   있어야 잡힌다.
3. **장황함의 뿌리는 함수가 아니라 구조다.** v2에서 함수 단위로 깎으려던 장황함(검증 55줄,
   few-shot 템플릿, merge)이 v3 구조 전환으로 대부분 소멸했다. "이 함수 필요해?"보다
   "이 함수를 요구하는 구조가 필요해?"가 먼저다.
4. **같은 파일을 두 세션이 동시에 소유하면 충돌한다.** 병렬 세션이 만든 미커밋 초안·conn 개명·
   문서를 이번 세션이 발견해 흡수했다 — 소유권을 한 세션에 몰고 다른 쪽엔 보류를 알리는 게 맞다.
5. **커밋 이력이 설계도보다 앞서갈 수 있다** (conn 개명, DDL 레포 제거). 설계도를 정답지로 쓰는
   워커는 시작 전에 최근 커밋과 대조해야 한다.

## 다음에 재사용할 것

- **LLM 행별 enrichment 골격 (v3형)**: 커서 extract → 단일 `@task.llm`(구조화 출력, enum은
  Literal 타입) → leaf가 성패 판정. 자리보존은 map_indexes 명시 pull 한 경계만.
- **provider 채택 전 체크**: 데코레이터가 실제 받는 kwargs를 소스에서 확인(문서 아님) +
  mapped면 unmap 실행 테스트. 버전 의존 우회(실행 순서 이용 등)는 주석에 업그레이드 경고를 남긴다.
- **단순화 요청을 받으면 함수가 아니라 구조를 의심한다.**
- **품질 논쟁은 eval로 치환한다** — "빼도 되나?"는 채점 도구가 있으면 측정 문제다.
