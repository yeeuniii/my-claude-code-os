# Interview (Airflow Python 파이프라인 전용)

## 이 스킬이 존재하는 이유

이 사용자는 계획을 길게 세우기보다 아이디어를 빠르게 던지는 스타일이다. "DAG 하나 만들어줘" 수준으로 짧게 요청할 때가 많다. 모호한 채로 바로 코드를 짜면 → 엉뚱한 방향으로 완성 → 사용자가 끊고 다시 설명 → 재작업 loop가 반복된다.

DAG는 결정들의 묶음이다. 재작업의 뿌리는 대부분 **"결정한 적 없는 결정"** — 아무도 묻지 않았고, 조사되지도 않았고, 가정으로 적히지도 않은 채 구현자가 조용히 정해버린 것이다. 이 스킬의 목적은 코드를 짜기 전에 그 결정들을 **남김없이 드러내 채우고**, "어떤 DAG를 만들지"를 **설계도로 합의한 뒤** 시작하는 것이다. 인터뷰가 목적이 아니라 **재작업을 없애는 것**이 목적이다.

## 전체 흐름

```
1. 조사       결정 목록을 코드·기존 DAG·자산으로 최대한 채움. 발견은 조용히 채택하지 말 것
2. 인터뷰(게이트)  조사로 못 푼 결정만 객관식으로 물음
3. 설계 제시   모든 결정이 채워진 설계도를 보여주고 OK 받기
   ─────────  ⛔ 여기가 이 스킬의 끝. 사용자 OK 없이는 절대 개발로 못 넘어감 (명확화 게이트)
4. 개발(호출자)  사용자가 OK → 개발로. 단 개발은 이 스킬이 하지 않는다(아래 참고)
```

이 스킬은 **조사~설계 합의까지만** 담당한다. 설계 제시에서 사용자 OK가 나면 역할은 끝이고, **개발은 호출자가 이어받는다** — 단독 호출이면 그대로 이어서 구현하고, 오케스트레이터가 불렀으면 그 흐름으로 넘어간다. 게이트는 **설계도의 `TODO(확인 필요)`가 전부 해소되고 + 설계도에 OK가 나야** 열린다 — TODO가 하나라도 남아 있으면 개발을 시작할 수 없다.

## 언제 쓰고 언제 안 쓰는가

인터뷰는 사용자의 시간을 쓰는 비용이다. 재작업 비용보다 쌀 때만 한다.

**쓴다:**
- Airflow 결과물을 요구하는데 source/destination/트리거/적재방식/실패처리 중 하나라도 안 잡힘
- "이 데이터 적재하는 DAG 만들어줘"처럼 입출력이 여러 갈래로 해석됨
- 기존 방식 중 뭘 따를지 갈림 (증분 vs 풀, catchup on/off 등)

**안 쓴다 (그냥 진행):**
- 요청이 이미 구체적 (어느 DAG의 어느 task를, 무엇으로 바꿀지 명시)
- 오타 수정, 변수명 변경, 로그 한 줄 추가 같은 사소한 1-스텝
- 사용자가 "일단 해봐 / 알아서" 라고 속도를 명시적으로 택함 → 존중하되, 되돌리기 어려운 것(멱등성 깨지는 적재, 운영 DAG 스케줄 변경)만 하나 확인

애매하면: 되돌리기 어려운 결정이 걸렸는가? 걸렸으면 물어라.

## 결정 목록

설계도가 담아야 할 결정은 `.claude/context/dag-design-spec.md`의 필드가 전부다. 이 스킬의 일은 **그 필드를 남김없이 채우는 것.** spec을 Read해서 빈칸을 잡아라.

모든 결정은 셋 중 하나의 출처를 가진다:

- **사용자가 답함** — 인터뷰에서 물어서.
- **조사로 정함** — 설계도의 `조사로 정한 것`에 근거와 함께 올려 확인받는다. 조용히 채택하지 않는다.
- **기본값 가정** — 설계도의 `가정`에 올린다.

이 셋 어디에도 못 넣는 결정은 `TODO(확인 필요)`로 남겨 눈에 보이게 한다.

## 1단계 — 조사 (묻기 전에 읽어라)

사용자에게 던지기 전에 답이 이미 있는지 본다. 사용자의 시간을 아끼는 게 예의다.

- 기존 유사 DAG, 공용 오퍼레이터/헬퍼, connection·variable을 읽는다. 어디를 볼지는 `.claude/context/workspace.md`의 '코드 위치'를 따른다
- **설치된 provider·데코레이터가 그 일을 이미 해주는지 확인한다.** 없다고 단정하지 말고 constraint 파일과 provider 소스를 실제로 본다 — 손으로 짜고 나서 발견하면 되돌리는 비용이 크다
- source를 실제로 본다: 갱신 시각·재갱신 여부·행수는 추측하지 말고 쿼리·스케줄 확인으로 잰다
- 프로젝트 CLAUDE.md, DAG 네이밍·폴더 규칙을 확인한다
- 필요하면 `Explore` / `general-purpose` 서브에이전트로 병렬 조사

**핵심 규칙 — 조사는 질문을 줄이는 것이지, 확인을 없애는 게 아니다.** 조사로 채운 결정 중:

- **설계를 좌우하는 것** (참고할 기존 DAG, source 테이블 특정, 전송 수단, 따를 오퍼레이터 패턴) → 설계도의 `조사로 정한 것`에 근거와 함께 올려 확인받는다. 조사로 헛다리를 짚어도 코드 전에 걸러지도록.
- **사소한 것** (폴더 구조, 파일 네이밍 규칙) → 조용히 따라도 된다.

기준은 "되돌리기 어려운가?"다. 조사로 풀린 결정은 질문 목록에서 빼고, 안 풀린 것만 2단계로 넘긴다.

## 2단계 — 인터뷰 게이트

**규칙은 하나다: 조사로 못 푼 결정만 묻는다.** 개수 제한은 없다 — 문제는 질문이 많은 게 아니라 물었어야 할 걸 안 묻는 것이다. 대신 질문 하나하나의 비용을 낮춘다:

- `AskUserQuestion`으로 **객관식**을 기본으로 한다. 선택지마다 trade-off를 보여줄 수 있다.
- 각 질문에 **추천 기본값**을 첫 선택지로 두고 "(추천)"을 붙인다. 사용자가 판단을 위임해도 진행이 멈추지 않게.
- 사소한 결정은 묻지 말고 합리적 기본값으로 정해 `가정`에 올린다 — 사용자는 설계 게이트에서 한 번에 반박한다.
- 진행도를 알려주면 게이트가 언제 열리는지 명확하다. 예: "결정 20개 중 17개 채움, 3개만 물을게요."
- 사용자가 "그냥 네가 정해"라고 하면 즉시 멈추고, 남은 결정은 기본값으로 채워 3단계로 넘어간다.

용어가 부담되면 쉬운 말로 풀어서 물어라. 예: "재실행하면 데이터가 중복될 수 있는데 어떻게 막을까요? (A) 키 기준으로 덮어쓰기 (B) 그 날짜 먼저 지우고 넣기"

## 3단계 — 설계 제시 (이게 진짜 게이트)

**설계도를 운영 레포 `designs/`에 파일로 먼저 떨군다** — 합의 전 초안부터. 형식·파일명 규칙은 `.claude/context/dag-design-spec.md`를 그대로 따른다(이 스킬은 그 spec의 생산자다 — 형식을 여기서 바꾸지 않는다). 각 결정의 안전 기준은 `.claude/context/airflow-antipatterns.md`와 `.claude/context/conventions/`가 근거다.

대화에서는 파일 경로를 알려주고 **설명과 확인 포인트만** 전한다 — 설계도 전문을 대화에 다시 붙이지 않는다. 특히 `조사로 정한 것`과 `가정`, 남은 `TODO(확인 필요)`를 짚어 사용자가 반박할 지점을 보여준다.

고치라고 하면 파일에 반영하고 다시 짧게 확인한다(한 항목이면 그 부분만). **TODO가 전부 해소되고 사용자 OK가 나면** 이 스킬의 역할 종료 — 호출자에게 **설계도 파일 경로**를 넘긴다(단독 호출이면 메인이 그 파일을 근거로 구현, 오케스트레이터면 그 흐름으로). 격리 워커는 대화를 못 보므로 파일이 유일한 인수인계 수단이다.

## 원칙 요약

- 인터뷰는 재작업을 없애기 위한 것. 인터뷰 자체가 목적이 아니다.
- "결정한 적 없는 결정"을 없애라. 모든 결정은 답변·조사·가정 중 하나의 출처를 가진다.
- 묻기 전에 읽어라. 단 설계를 좌우하는 발견은 조용히 채택하지 말고 설계도에서 확인받아라.
- 조사로 못 푼 결정만 물어라. 개수 제한 없음 — 대신 객관식 + 추천 기본값으로 답을 싸게.
- 항상 추천 기본값을 제시해 진행이 멈추지 않게 한다.
- **DAG 설계도(task+의존성)로 합의하고, 사용자 OK 전에는 코드를 짜지 않는다.** 이 게이트가 헛수고를 막는다.
